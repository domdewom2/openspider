# M2-N33 – calamine 0.38 / zip 9 (RUSTSEC-2026-0436)

Stand: 03.11.2026. Branch `m3/n33`, Basis `main` (`9100f85f`). Bauen und Testen auf dem Linux-Build-Server
(eigener Worktree `n33`, eigenes `target/`, Code per `git bundle`, kein Push vom Server). Modell: Claude Opus 5.5.

## Anlass

RUSTSEC-2026-0436 (calamine 0.36.1): Panic und unbegrenzte Allokation im CFB-/OLE2-Leser bei manipulierten
`.xls`-/`.xlsb`-/VBA-Dateien, behoben in calamine 0.38.0. `cargo deny check advisories` war damit auf allen Branches
rot (auf dem Stand `9100f85f` nachvollzogen: `error[vulnerability]` RUSTSEC-2026-0436).

## Ergebnis

1. **calamine 0.38.0** (`Cargo.toml`: `calamine = "0.38"`), Lockfile gezielt mit
   `cargo update -p calamine --precise 0.38.0`. Kein allgemeines `cargo update`, Tokio bleibt 1.53.3.
2. **API:** Für die Aufrufer in os-engine, os-export und os-cli keine Anpassung nötig (0.37 hebt zip/quick-xml und
   ergänzt Workbook-Eigenschaften, 0.38 ergänzt Zellformate; `open_workbook(_auto)`, `Reader::worksheets`,
   `Range::rows`, `Data` unverändert). Clippy und alle bestehenden XLSX-/XLS-Tests ohne Änderung an Code oder
   Erwartungen grün (K2-63).
3. **Robustheit:** Neue Fixtures `tests/fixtures/crawl-list-corrupt/` (vier defekte OLE2-Container, Aufbau im
   README) und Test `crates/os-engine/tests/list_corrupt_xls.rs`. Gegenprobe mit einem Wegwerf-Programm auf dem Server
   (außerhalb des Repos) gegen beide calamine-Versionen:

   | Fixture | calamine 0.36.1 | calamine 0.38.0 | Import (dieser Stand) |
   |---|---|---|---|
   | `truncated-header.xls` (300 Byte) | Fehler | Fehler | `EngineError::Invalid` |
   | `truncated-directory.xls` (Verzeichnisstrom 200 Byte, kein Vielfaches von 128) | **Panic** (Slice-Index 116 bei Länge 72) | Fehler „Cannot find Workbook stream“ | `EngineError::Invalid` |
   | `difat-loop.xls` (FAT-Länge `0xFFFFFFFF`, DIFAT-Kette auf sich selbst) | **hängt** (Endlosschleife mit wachsender Liste, nach 20 s abgebrochen) | Fehler „Sector 0 points past end of file“ | `EngineError::Invalid` |
   | `no-fat.xls` (kein FAT-Sektor, Verzeichnis in Sektor 0) | **Panic** (Index 0 bei Länge 0) | **Panic** (unverändert, `Sectors::get_chain`) | `EngineError::Invalid` (abgefangen) |

   Befund: calamine 0.38.0 behebt die gemeldeten Fälle, ein CFB-Container ohne FAT-Sektor löst aber weiterhin einen
   Indexfehler aus. Deshalb laufen die calamine-Lesevorgänge der beiden Produktivpfade mit Nutzerdateien – Listen-Import
   (`list_input::read_workbook`, CRAWL-027) und SERP-Upload (`serp_input::read`, CRAWL-031) – jetzt über
   `list_input::read_spreadsheet`: `catch_unwind` macht aus einem Parser-Panic `EngineError::Invalid("<Datei>: Tabellendatei
   ist beschädigt …")`. Kein `panic = "abort"`-Profil im Workspace, der Schutz greift also auch im Release. Alle
   übrigen calamine-Aufrufe in os-export/os-cli sind Tests, die eigene Exporte lesen.

   Der Test prüft je Fixture für `read_items`, `read_list` und `serp_input::read`: Ergebnis ist `EngineError::Invalid`
   (Meldung nennt die Datei), kein Panic im Import-Thread, Ergebnis innerhalb von 30 s, und der Speicher-Höchststand
   des Import-Threads (zählender `#[global_allocator]` je Thread, plattformneutral) bleibt unter 16 MiB. Gegenprobe:
   `urls.xlsx`, `serp.xls`, `serp.xlsx` lesen unverändert durch denselben Pfad.
4. **deny.toml:** zip 8.6.0 ist **nicht** aus dem Baum verschwunden – es kommt außer über calamine 0.36.1 auch über
   **rust_xlsxwriter 0.99.1** (zip `^8.3`; erst rust_xlsxwriter ≥ 0.100 nutzt zip `^9`). Die bisherige Begründung
   („kommt nur transitiv über calamine“) war in diesem Punkt schon vorher unvollständig. Nach Auftrag („sofern zip 8
   nicht mehr im Baum ist“) bleiben RUSTSEC-2026-0367/-0368/-0369/-0429 deshalb ignoriert; ohne die vier Einträge
   meldet `cargo deny check advisories` genau diese vier Advisories für `zip v8.6.0 ← rust_xlsxwriter v0.99.1`
   (geprüft). Die Begründungen sind korrigiert:
   - Pfad jetzt rust_xlsxwriter 0.99.1 (os-export, darüber os-app/os-cli/os-mcp).
   - rust_xlsxwriter schreibt über `ZipWriter`; gelesen wird ZIP nur in `read_theme_from_path`
     (`Workbook::use_custom_theme`, von OpenSpider nicht aufgerufen) per `by_name` im Speicher; `extract` nirgends.
   - Korrektur laut Backlog: OpenSpider **entpackt** Archive – `crates/os-cli/src/browser.rs` (`ZipArchive::extract`
     für das Chromium-Archiv) und `crates/os-render/src/provision/install.rs` (`zip.extract`), beide über die direkte
     Abhängigkeit zip 9.0.4 (behoben), nicht über zip 8.6.0.
   - RUSTSEC-2026-0436 wird **nicht** ignoriert; es ist durch das Update behoben.
5. **Lizenzen:** calamine 0.38.0 steht unter MIT (Positivliste), quick-xml 0.42.0 und zip 9.0.4 waren schon im Baum.
   `cargo deny check licenses` grün. Third-Party-Notices werden laut `docs/release/lizenzen.md` nur in Release-CI
   erzeugt (im Git nur Platzhalter); keine Datei zu aktualisieren. Ergebnis der Erzeugung auf dem Server siehe
   Prüfungen.

## Offene Punkte und Hinweise

- **zip 8 / rust_xlsxwriter (Vorschlag Folgepaket):** Die vier zip-Ausnahmen lassen sich erst mit rust_xlsxwriter
  ≥ 0.100 (zip `^9`, aktuell 0.102.0) streichen. Das ist ein SemVer-inkompatibler Sprung des XLSX-Writers aller
  Exporte (Manifest-Änderung, Goldens/`constant_memory` prüfen) und gehört nicht in dieses Paket. Zusätzlich gilt
  zip 8.x laut calamine-Changelog upstream als zurückgezogen (yanked); `cargo deny` meldet das für zip 8.6.0 derzeit
  nicht.
- **Restpanic in calamine 0.38.0:** CFB ohne FAT-Sektor → Index-Panic in `Sectors::get_chain`
  (`fats[sector_id]`). Im Import abgefangen; ein Upstream-Bericht an calamine (mit `no-fat.xls`) wäre sinnvoll –
  nicht vom Paket eingereicht (öffentlicher Beitrag, Entscheidung beim Nutzer/Orchestrator). Der Panic-Hook schreibt
  die Meldung weiterhin auf stderr.
- **cargo-deny auf dem Server:** Die installierte Version 0.18.5 konnte die aktuelle Advisory-Datenbank nicht mehr
  lesen (TOML-Fehler in RUSTSEC-2026-0212); per `cargo install --locked cargo-deny` auf 0.20.2 aktualisiert
  (`~/.cargo/bin`, gilt für alle Pakete auf dem Server). CI nutzt `cargo-deny-action@v2` (aktuelle Version).
- Kein Upgrade weiterer Pakete; `warning[yanked]` für `clipboard-win` (Desktop) besteht unabhängig von diesem Paket.

## Abschluss

RUSTSEC-2026-0436 ist durch calamine 0.38.0 behoben, der Import ist gegen defekte `.xls` abgesichert, alle
Server-Prüfungen grün, CI gestartet (Ergebnis durch den Orchestrator). Abweichung vom Auftrag: die vier zip-8-Ausnahmen
bleiben (zip 8.6.0 weiter über rust_xlsxwriter 0.99.1), Begründung korrigiert; Folgepaket rust_xlsxwriter ≥ 0.100
vorgeschlagen. Server-Worktree samt `target/` nach Abschluss entfernt.
