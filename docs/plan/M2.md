## 2a Ausführungsregeln Cloud (Orchestrator und Pakete)

Lehren aus M1 (E1–E8) sind übernommen: E4 → C7, E5 → C8, E6/E8 → Nacharbeitspakete N0x je Welle, E7 → C9, Welle-6-Besitzregel K-65 → C10, „abhängige Pakete nie in dieselbe Welle“ → C1 (und per Skript geprüft), Startprüfung per `git log … --grep='Merge …'` → C1, Messungen nur auf ruhiger Maschine → C11.

- **C1 Start eines Pakets:** Der Orchestrator startet eine Cloud-Session mit dem Branch `m2/<kurz-id>` von `origin/main`, sobald **alle** `depends_on` gemergt sind: je Abhängigkeit `git log --oneline origin/main -i --grep='Merge <kurz-id>'` mit genau einem Treffer (Merge-Commits heißen `m2: Merge <kurz-id>`). Eine Welle besteht nur aus Paketen ohne Abhängigkeiten untereinander; innerhalb einer Welle startet jedes Paket, sobald seine eigenen Voraussetzungen erfüllt sind (in Welle 1 starten Kern- und Fachpakete nach M2-F02/F03 und dem Schnittstellen-Vorbau M2-F05a/F05b, UI-Pakete nach M2-G0 und M2-F05b). **N-Pakete** (N01, N02) starten erst, wenn **alle** Pakete ihrer Quellwelle gemergt sind (N01: alle 45 Welle-1-Pakete; N02: alle übrigen Welle-2-Pakete); `depends_on` führt sie vollständig auf, damit jeder Platzhalter-Ort aus C9 beim Start existiert (Prüfskript P11). Session-Auftrag = `prompt_notes` + Verweis auf die genannten Abschnitte dieses Plans.
- **C2 Keine lokalen Pfade:** In Code, Tests, Skripten und Prompts nur Pfade relativ zur Repo-Wurzel; temporäre Daten über `tempfile`; App-/Nutzerordner über `dirs` bzw. `OPENSPIDER_HOME`. Ports ephemer, außer den festen Paritätsports (die Session ist isoliert, kein `lockf` nötig).
- **C3 Umgebung:** `scripts/cloud/setup.sh` (M2-F01) richtet ein: Rust laut `rust-toolchain.toml`, Node 22 (`engines`), `npm ci`, `npx playwright install --with-deps chromium webkit`, `OPENSPIDER_CHROMIUM` = Chromium aus Playwright, optional `libwebkit2gtk-4.1-dev librsvg2-dev libayatana-appindicator3-dev` für `openspider-desktop` unter Linux, `OPENSPIDER_SECRET_STORE=memory` (C13; **kein** Secret Service/gnome-keyring). Das Skript ist idempotent und läuft in jeder frischen Cloud-Session sowie im eigenen Linux-Job `.github/workflows/cloud-setup.yml` (Besitz M2-F01).

- **C10 Besitz:** Jede Datei – auch jedes Golden, jede Testdatei, jede Fixture, jede Baseline – gehört in einer Welle genau einem Paket. Braucht ein Fix eine fremde Datei, bricht das Paket ab und meldet Datei, Diff-Auszug und Grund. **Ausnahme Stub-Ablösung (K2-60):** Ein Paket, das einen eigenen F05-Stub durch echtes Verhalten ersetzt, darf in den Vertragstests und Stub-Listen von F05a/F05b (z. B. `crates/os-app/tests/manifest_contract.rs`, `crates/os-app/tests/f05_*.rs`, `crates/os-engine/f05a-stubs.toml` und gleichartige Stub-Prüfungen in anderen Crates) genau die Einträge entfernen oder auf das echte Verhalten umstellen, die **seine eigenen** Stubs betreffen – nichts anderes. Konflikte in diesen Listen löst der Integrator beim Merge. **Ausnahme additive Schnittstellenergänzung (K2-61, Welle 1):** Fehlt einem Paket ein Erweiterungspunkt aus F05, darf es außerhalb seiner `owns` *strikt additiv* ergänzen – neues Feld mit Default, neue Funktion/Methode, neue Enum-Variante nur mit `#[non_exhaustive]`-Verträglichkeit, zusätzlicher Aufruf in einer Init-/Registerliste, zusätzliche Spalte in einem SELECT –, aber keine bestehende Signatur, kein bestehendes Verhalten und keine fremden Tests ändern. Jede solche Ergänzung steht mit Datei und Diff im Bericht unter „Fremdergänzungen (K2-61)“; Fable prüft sie im Review, der Integrator löst Merge-Konflikte. **Ausnahme Erwartungsänderung (K2-63, Welle 1):** Ändert das spec-gemäße Verhalten eines Pakets die erwartete Ausgabe fremder Tests oder Goldens (z. B. neue Spalten, neue Filterzustände, geänderte Sichtbarkeit), darf das Paket genau diese Erwartungen anpassen – nur die Erwartung, nicht die Testlogik – und begründet jede Anpassung im Bericht mit Datei, alter/neuer Erwartung und Spec-ID.

### 3.7 Tauri-Hülle (M2-F03)
