## Z-06 – Speicherwächter unter macOS

- **Ursache:** Gepinnte sysinfo 0.37.2 berechnet unter macOS `available = (free + inactive + purgeable − compressor) × Seitengröße`, `used = (active + wired + compressor + speculative) × Seitengröße`. Inaktiver Speicher ist berücksichtigt, Kompressorspeicher senkt `available` zusätzlich. `tick` loggte jeden Durchlauf; die bisherige Fortschrittsstufe zeigte nur Prozessgrenzen und konnte trotz Drosselung Normal melden.
- **Änderung:** Unter macOS `physical − used` verwenden: Kompressor einmal belasten, inaktive Seiten verfügbar halten; andere Plattformen behalten `available`. Die bestehende Reserve von 10 % (1,6 GiB bei 16 GiB) bleibt konservativer Schutz für OS/andere Apps und reduziert nur Parallelität. Prozessgrenzen 80/90 % bleiben unverändert. Sichtbare Speicher-/Drosselungsstufe, Logs nur bei Zustandswechsel und Wiederherstellung der Threadzahl bei Erholung.
- **Tests:** Getaggte Speicherstufen-Fixture vor Fix rot, danach grün. Ein 60-Tick-Test erfasst echte Tracing-Ereignisse: einmal Warnung, einmal Erholung, Rückkehr auf die konfigurierte Threadzahl. Statusleisten-Fixture prüft sichtbare Drosselung und Aufhebung auch nach Dismiss der Notice. Die vollständige Engine-Suite einschließlich beider neuen Speicherprüfungen ist auch im erneuten Gesamt-Workspace-Lauf grün.

### Befund 2 – Schnittstellenbedarf gemäß C10, noch nicht angewandt

Die Ursache ist bestätigt: `CrawlHandle::set_threads` schreibt `Control.threads`; die Speicheraktion überschreibt denselben Wert, und die Erholung setzt ihn aus der unveränderlichen Konfigurationskopie zurück. Eine Änderung ausschließlich in `memory.rs` kann die gewünschte Laufzeitparallelität weder zuverlässig kennen noch getrennt von der wirksamen Drosselung erhalten.

Benötigte **neue Fremdpfade**, außerhalb von N04 und K2-80a/b/c:

- `crates/os-engine/src/worker.rs`: eigenes atomares Speicherlimit neben dem bestehenden gewünschten Threadwert.
- `crates/os-engine/src/crawl.rs`: Limit initialisieren, effektiv `min(gewünscht, Speicherlimit)` planen und Speicheraktionen ausschließlich auf das Limit anwenden. `set_threads` bleibt beim gewünschten Wert und weckt weiterhin sofort die Schleife.

Konkreter vorgeschlagener Diff (nicht angewandt):

```diff
diff --git a/crates/os-engine/src/worker.rs b/crates/os-engine/src/worker.rs
@@ struct Control
     /// Gewünschte Zahl paralleler Threads.
     pub threads: AtomicU32,
+    /// Obergrenze durch Speicherschutz; u32::MAX bedeutet keine Drosselung.
+    pub memory_threads: AtomicU32,
diff --git a/crates/os-engine/src/crawl.rs b/crates/os-engine/src/crawl.rs
@@ Control initialisieren
         threads: AtomicU32::new(init.cfg.speed.threads),
+        memory_threads: AtomicU32::new(u32::MAX),
@@ Worker planen
-        let target = ctl.threads.load(Ordering::SeqCst) as usize;
+        let target = ctl.threads.load(Ordering::SeqCst)
+            .min(ctl.memory_threads.load(Ordering::SeqCst)) as usize;
@@ Speicheraktion anwenden
-                        crate::memory::MemoryAction::Throttle(n) => { ctl.threads.store(n.max(1), Ordering::SeqCst); },
+                        crate::memory::MemoryAction::Throttle(n) => { ctl.memory_threads.store(n.max(1), Ordering::SeqCst); },
diff --git a/crates/os-engine/src/memory.rs b/crates/os-engine/src/memory.rs
@@ Erholung
-            MemoryAction::Throttle(input.config.speed.threads.max(1))
+            MemoryAction::Throttle(u32::MAX)
```

Prüfung über die echte Steuerschleife, innere Zeitgrenze und verzögerte SimSite-Antworten. Dieser Test wurde ohne freigegebenen Produktfix noch nicht hinzugefügt; der Speicherbefund ist nicht als behoben ausgewiesen. Keine Fremddatei geändert.
